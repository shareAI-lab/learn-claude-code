## 3. 关键设计决策

### 3.1 队友为什么选线程而非子进程
- Python 线程共享内存，`TaskStore` / `MessageBus` 天然单例
- 子进程要额外 serialize config / 工具 registry，复杂度高
- 代价：GIL 影响 CPU 密集，但 LLM 调用是 I/O 密集，线程完全够用
- 未来扩展：若真要隔离（bug 容忍、资源限制），可以抽出 `TeammateRunner` 抽象类让子进程实现

### 3.2 消息总线为什么用文件而非内存队列
- 持久化：崩溃后消息不丢，重启还能 drain
- 跨进程兼容：未来 s12 worktree 里的 agent 也能投递
- 审计：`.team/inbox/*.jsonl` 直接 tail 就能看团队交流
- 代价：每发一条消息 2 次文件 IO，但团队对话密度远低于 tool 调用，可忽略

### 3.3 协议用 request_id 而非 Promise
- Python 原生 asyncio.Future 在跨线程时很麻烦（需要 `run_coroutine_threadsafe`）
- request_id 状态机更简单：发请求 → 对方回响应 → tracker 字典改状态
- 副作用：lead 不会"自动被通知响应到达"，需要在下一轮读 inbox 时看到。这和 `BackgroundRun` 的回流模式一致。

### 3.4 自治 ClaimTask 幂等的意义
- 同一 teammate 重复 claim 同一 task → 成功（无害）
- 不同 teammate claim 已认领的 task → Error
- 防止并发下两个队友以为都认领到了，根本原因是 `_claim_task` 先读 owner 再写。竞态窗口极小但非零 —— M4 若需要严格正确性可以加 fcntl lock

### 3.5 身份重注入的触发条件
- `non-system messages ≤ 3` → 说明 auto-compact 发生了，history 被压成一条 summary
- 此时模型已经"忘了自己是谁"，必须补一条 `<identity>` 标签
- 这是教学项目 s11 的核心技巧，直接借鉴

## 4. 已知限制

1. **MCP sse/http 无真实 E2E 测试**：只测了纯逻辑（`_connect` 对 url 缺失的拒绝、`_prefixed_tool_name` 策略）。真实连接需要起 mock server，放 M4
2. **队友 loop 无自动化测试**：启动线程跑真 LLM 调用风险高、慢，当前只测了 `_build_teammate_registry` / `_try_autoclaim` 等纯函数
3. **ClaimTask 竞态窗口**：两个队友同时扫表，可能同一瞬间都以为自己认到了 —— 实测概率极低但非零
4. **auto-compact 对队友的影响**：队友的 state.messages 当前**没接入 auto-compact**。长对话可能撑爆 context。M4 要给 `run_turn` 在队友场景也接上 `summarize_llm`
5. **退出总结调的是 `roles.summarize`，但没做成本上限**：极端情况下一次总结可能很贵。M4 加 token 预算
6. **`.team/config.json` 无锁并发**：多线程 `register` 可能覆盖。目前靠 `_lock` 保护，跨进程就不管用了
7. **PyPI 未真实发布**：包名 `oai-code` 占用未检索；发布指南完备但需维护者手动走流程
