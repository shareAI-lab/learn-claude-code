## 3. 关键设计决策

### 3.1 Session 为什么选 JSONL 而不是单 JSON 文件
- 增量追加成本 O(1)，不需要每轮重写整个文件
- 崩溃恢复容忍：最后一行损坏时前面的消息仍可恢复
- 落盘前对 `content` 跑 `redact`，避免 API key / .env 泄漏进历史

### 3.2 MCP 客户端为什么起独立 asyncio 线程
- MCP SDK 是纯 async；oai-code 主 loop 是同步的
- 独立线程跑 `loop.run_forever()`，主线程用 `asyncio.run_coroutine_threadsafe` 投递任务，结果同步等待
- 好处：与现有同步 `tool.handler` 签名无缝兼容，不用把整个 agent loop 改 async
- 成本：每次调用多一次线程切换；对 MCP 这种网络/子进程调用可以忽略

### 3.3 为什么后台任务不用 asyncio 而用 threading
- BackgroundRun 本质是 `subprocess.run`，CPU 密集时释放 GIL
- 线程池模型简单直观：一个任务一个线程，完成后入 Queue
- 与 MCP 的 asyncio 线程互不干扰，不会造成死锁

### 3.4 auto-compact 触发点 vs --no-save
- auto-compact 只动 in-memory messages，不会影响 session jsonl 的完整历史
- 所以 resume 时拿到的是**压缩前的完整对话**，模型可选择重新压缩或继续

## 5. 已知限制

1. **MCP 只支持 stdio**：sse / http 传输 M3 再做。有商业 MCP server（如 Linear 云端版本）可能只有 http，当前需用户自己装 stdio 代理。
2. **Session resume 不会重算 system prompt**：恢复时直接用存在 jsonl 里的老 system（含当时的 skills/memory 状态）。如果中途改了 `CLAUDE.md`，要手动 `/clear` 才会刷新。
3. **后台任务的 SIGINT 不会传给子进程**：Ctrl-C 中断主 loop 时，后台 subprocess 仍会跑完。M3 会加 `BackgroundKill`。
4. **`--resume latest` 不区分 auto-compact 前后**：如果上次会话被 auto-compact 过，jsonl 里同时有"原消息"和"压缩后消息"（因为我们压缩的是内存，jsonl 已经 flush 走的不管）—— 这会导致 resume 后前缀重复。M3 会加 session 版本化标记。
5. **`/history` 不展开 tool_calls 参数**：只显示 `+N tool_calls`，不给内容。有需要再加。
6. **MCP 未覆盖真正的 server 启动与工具调用的集成测试**：`test_mcp.py` 都是纯逻辑单测，缺一个最小 stub server 的 E2E。M3 或 M2 收尾时补。

1. **多 Agent 协作**（s09-s11）：teammate 消息总线、shutdown_request handshake、plan_approval 流程 —— 需要一个轻量的 per-teammate 子进程模型；建议先把后台任务的线程模型扩展到"后台 agent"

3. **MCP sse/http + PyPI 发布**：前者补齐生态接入，后者让用户能 `pipx install oai-code`
