# 从 Claude Code 取经：如何写出高效的提示词

你是不是还在写这样的提示词：

```text
你是一个拥有10年经验的资深全栈工程师，精通Python、Go、Java，
善于沟通，注重代码质量，对技术有热情...
请仔细、全面、认真地分析问题，一步一步思考...
以下是项目规范（200条）...
```

效果不好，于是加更多文字。文字越多，模型越抓不住重点。

我拆解了 Claude Code 的系统提示词设计（515 段独立片段，被 [Piebald 团队逆向](https://github.com/Piebald-AI/claude-code-system-prompts)），结合 [Anthropic 官方提示词工程指南](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/use-xml-tags)，发现真正高效的提示词写法和传统写法完全不同。

这篇文章讲清楚两件事：++为什么旧写法不需要了，以及怎么写出真正高效的提示词。++

---

## 为什么旧写法不需要了？

两层原因：模型变聪明了 + 工具层把工程活揽走了。

### 模型变聪明了

2023年流行的 prompt 技巧，本质都是补模型能力短板的"补丁"。现在的推理模型能力上来了，补丁就多余了：

++"Let's think step by step"++ —— 推理模型已内化分步推理，外部触发反而增加延迟。

++"你是一个专家..."角色扮演++ —— 模型已对齐为通用 helpful，堆人格描述反而干扰注意力。

++手写 Thought/Action/Observation 格式++ —— 模型已学会原生 tool calling，API 层标准化了。

++Few-shot 示例链++ —— 大模型对齐后直接理解指令，示例链边际收益递减。

++"请仔细、全面、认真"++ —— 模型默认就仔细，形容词是噪音。

一句话：模型从"被诱导才推理"变成"默认就推理"。旧技巧是补能力短板的补丁，能力补齐后补丁多余了。

### 工具层接管了

Claude Code 的工具层帮用户做了大量以前必须手写在 prompt 里的工作：

| 你以前要写在 prompt 里的 | 工具层自动做了 |
|---|---|
| "上下文别超出 token 限制" | 四层压缩管道，API 调用前自动跑 |
| "工具结果太长请摘要" | 超过 200KB 自动落盘，留 2KB 预览 |
| "记住之前讨论的X" | 记忆系统自动选择相关记忆注入 |
| "先读文件再动手" | TodoWrite 工具，模型自己写 todo 分解任务 |
| "你的工作目录是X" | 每轮按真实状态动态拼装 system prompt |
| "这个操作危险请确认" | 权限管道 + hooks 门禁 |
| "遇到错误请重试" | 自动 token 升级 + fallback 模型 |

++这些以前必须写在 prompt 里的指令，现在被代码接管了。代码比自然语言可靠。++

**结论：用户的 prompt 从"操作手册"退化为"目标声明"——告诉模型要什么就够了。**

---

## 两种提示词，写法完全不同

在讲具体技巧之前，必须先区分：你写的是**系统提示词**还是**需求提示词**。混为一谈是大多数人写不好提示词的根因。

### 系统提示词（System Prompt）

管"你是什么"——身份、规则、环境。写一次，跑无数轮。

典型场景：开发 Agent 产品、定制 AI 助手、配置 Cursor/Claude Code 的 CLAUDE.md。

Claude Code 的系统提示词有 515 段，但身份只有一句：`Act, don't explain.`

### 需求提示词（User Message）

管"你要做什么"——具体任务、约束、上下文。每次任务都不同。

典型场景：日常用 ChatGPT/Claude 写代码、改 bug、做方案。

这两种场景的写法技巧完全不同，下面分开讲。

---

## 系统提示词：5 个技巧

### 技巧一：身份极简，动词开头

Claude Code 的身份只有一句 `Act, don't explain.` ——用动词指挥模型（行动），不是形容词描述角色（身份）。

515 段 prompt 里大量使用 `CRITICAL`、`STRICTLY PROHIBITED` 划红线，但没有任何"你是一个专业、认真、负责"的角色扮演。

```text
❌ 形容词堆砌
你是一个拥有10年经验的资深工程师，善于沟通，
注重代码质量，对技术有热情，请认真分析...

✅ 动词开头
Act, don't explain.
```

++模型不需要你告诉它"要专业"——它默认就是。形容词是噪音。++

### 技巧二：用分隔符切分区

Claude Code 的 515 段 prompt 按功能分区域，每个区域只管一件事。Anthropic 官方文档也明确推荐用 XML 标签来组织复杂 prompt，内部测试显示结构化 XML 提示词比纯文本一致性提升 20-40%。

写 system prompt 时用标签包裹每个区域：

```text
<identity>
你是代码审查助手，专注于安全和性能问题。
</identity>

<tools>
- read_file: 读取项目文件
- run_test: 执行测试套件
- search_code: 全局搜索代码
</tools>

<rules>
修改前必须读文件。
改完必须跑测试。
不要删除已有注释。
</rules>

<environment>
项目目录: /home/project
语言: Python 3.12
框架: Flask + SQLAlchemy
</environment>
```

++XML 标签给模型明确的语义边界。++ `&lt;rules&gt;` 里的内容和 `&lt;environment&gt;` 里的内容不会互相污染。Anthropic 文档原话：++Claude 经过专门训练来识别 XML 结构，所以特别有效。++

### 技巧三：catalog/content 两级加载

Claude Code 的技能系统不是全量灌进 prompt，而是分两层：第一层只放目录（每个技能一行描述），第二层模型需要时才加载完整内容。

```text
✅ 先放目录（每条一行）
<skills_catalog>
- git-workflow: Git 提交规范和分支管理
- api-testing: API 测试模板和自动化方案
- deploy: 部署检查清单
</skills_catalog>

需要某个技能的详细内容时，调用 load_skill 加载。

❌ 不要全量灌入
以下是 git-workflow 的完整规范...（3000字）
以下是 api-testing 的完整模板...（2000字）
```

++先给菜单，模型自己点菜。++ 不相关的信息是噪音，会降低输出质量。

### 技巧四：注入真实状态，不写教科书

Claude Code 每轮读取真实文件状态（工作目录、记忆文件、已连接工具），注入到 system prompt。不是写死"你的工作目录可能是X"，而是每轮动态读取。

```text
✅ 注入真实的（模型不知道的）
<environment>
当前工作目录: /home/myapp
已有文件: auth/middleware.py, models/user.py, routes/api.py
数据库: PostgreSQL，已有 users 表
</environment>

❌ 不要写教科书（模型都知道的）
Flask 是一个 Python Web 框架，
使用 SQLAlchemy 作为 ORM，
支持 Blueprint 模块化路由...
```

++模型知道 Flask 怎么用。它不知道的是你的项目长什么样。++

### 技巧五：静态放前面，动态放后面

Claude Code 的 prompt 把不变的内容和会变的内容明确分开。不变的部分放前面让 API 缓存命中，会变的部分放后面不污染缓存。

```text
[不变] <identity> 身份定义 </identity>
[不变] <tools> 工具列表 </tools>
[不变] <rules> 编码规范 </rules>
--- ← 缓存断点 ---
[偶尔变] <iteration_context> 当前迭代需求 </iteration_context>
[每次变] <task> 具体任务描述 </task>
```

++把不变的规则放前面，每次变化的任务放后面。++ API 的 prompt cache 能命中前半段，省 token 又省时间。

## 需求提示词：5 个技巧

日常用 AI 工具（ChatGPT、Claude、Cursor）时，你写的是 user message。这里的关键不是"怎么定义角色"，而是"怎么把任务说清楚"。

Anthropic 官方文档给了一个黄金法则：++把你的 prompt 拿给一个不了解任务的同事看，如果他能理解，模型也能。++

### 技巧六：用分隔符切分，不要写流水

这是最实用、上手最快的技巧。当你有多个信息要给模型时，用 `##` 或 `---` 切分成不同区块，比写一大段流水效果好得多。

Claude Code 的 515 段 prompt 就是这么组织的——每个区域只管一件事，区域之间用分隔符隔开。

```text
❌ 流水写法（信息混在一起）
帮我写个注册接口，数据库有users表，
有id、email、password_hash字段，
邮箱要校验格式和查重，密码用bcrypt，
返回JWT，不要引入新依赖，
参照auth/middleware.py的风格...

✅ 分隔符写法（结构清晰）
## 背景
数据库已有 users 表：id、email、password_hash
项目已有 auth/middleware.py

## 任务
实现用户注册 API（POST /api/register）

## 约束
- 邮箱格式校验 + 重复检测
- 密码用 bcrypt 加密
- 返回 JWT token
- 不引入新依赖

## 参照
参照 auth/middleware.py 的错误处理风格
```

同样的信息，但用 `##` 分区后模型能更准确地理解"哪段是背景、哪段是约束、哪段是参照"。Anthropic 官方测试显示结构化提示词比纯文本一致性提升 20-40%。

++不需要 XML 标签，markdown 的 `##` 和 `---` 就够了。++ 关键是让模型能区分不同类型的信息。

### 技巧七：给上下文，不给教科书

这是从 Claude Code 学到的核心原则。Claude Code 不教模型什么是 JWT——它注入当前目录、已有文件、数据库结构。

```text
❌ 教科书式（模型都知道）
## 背景
JWT 是一种用于身份验证的令牌机制，
它由 Header、Payload、Signature 三部分组成，
使用 HMAC SHA256 算法签名...

✅ 上下文式（模型不知道的）
## 背景
数据库已有 users 表：
  - id (uuid, 主键)
  - email (varchar, 唯一索引)
  - password_hash (varchar)

项目已有 auth/middleware.py，新代码要和它兼容。
```

++模型知道 JWT 怎么工作。它不知道的是你的数据库长什么样。++

### 技巧八：给参照物比给规范有效

Claude Code 的技能加载系统有一个设计：不给模型一份"代码规范文档"，而是让模型读已有代码来模仿风格。

```text
❌ 写一堆规范
代码风格要求：
1. 函数名用小写下划线
2. 每个函数必须有 docstring
3. 参数类型必须标注
4. 异常必须 try-except 包裹
5. 日志用 logging 模块
...（还有20条）

✅ 给参照物
参照项目中已有的 auth/middleware.py，
用相同的代码风格实现。
具体来说：命名规范、错误处理方式、
日志格式都和它保持一致。
```

++模型模仿已有代码的能力很强。++ 与其写 20 条规范，不如让它看一个你满意的范例。

### 技巧九：给约束和负面示例——告诉它别做什么

Claude Code 的 prompt 里大量使用 `STRICTLY PROHIBITED` 划红线。Anthropic 官方建议：告诉模型做什么，同时告诉它不要做什么。

```text
## 任务
重构 process_payment 函数，提取重复逻辑

## 约束
- 保持函数签名不变（输入输出不能改）
- 不要引入新依赖
- 不要修改函数名
- 不要重写整个文件，只改相关函数
```

++告诉模型不要做什么，和告诉它要做什么一样重要。++ 特别是改已有代码时，不加约束模型可能把你整个文件重写。

### 技巧十：复杂任务拆步骤，不要一次要全部

Claude Code 的子代理 prompt 用编号步骤组织任务（Understand → Explore → Design → Detail）。日常写复杂需求时也要拆：

```text
## 任务
帮我实现用户注册功能

## 步骤
1. 创建 users 表的 migration
2. 写注册 API（POST /api/register）
   - 邮箱格式校验 + 重复检测
   - 密码强度检查
   - bcrypt 加密
3. 写测试覆盖所有分支

先做第 1 步，完成后等我确认再做第 2 步。
```

++不要把 5 个步骤塞进一段话。++ 拆成编号步骤，模型能更准确地执行，你也能在每一步检查质量。

## 速查表

| 场景 | 技巧 | 核心 |
|---|---|---|
| 系统提示词 | 身份极简 | 动词开头，不用形容词 |
| 系统提示词 | XML 标签切分区 | 用 XML 分区，一次设定 |
| 系统提示词 | 两级加载 | 先目录后详情 |
| 系统提示词 | 注入真实状态 | 给模型不知道的环境信息 |
| 系统提示词 | 静态动态分开 | 不变的放前面保缓存 |
| 需求提示词 | 分隔符切分 | 用 ## 背景 / ## 任务 / ## 约束 分区 |
| 需求提示词 | 给上下文不给教科书 | 给项目环境不给通用知识 |
| 需求提示词 | 给参照物比规范有效 | 让模型看已有代码模仿 |
| 需求提示词 | 给约束和负面示例 | 明确说不要做什么 |
| 需求提示词 | 拆步骤不一次要全部 | 编号步骤 + 分步确认 |

## 总结

旧提示词写法失效有两层原因：

++第一层：模型变聪明了。++ 推理、规划、工具调用已经内化，不需要外部诱导。

++第二层：工具层接管了。++ 压缩、缓存、记忆、权限这些以前要写在 prompt 里的，现在被代码处理了。

Claude Code 用 515 段独立片段、每轮动态拼装的方式告诉我们：好的提示词只给当前需要的信息，不给用不上的。

++系统提示词管"你是什么"——身份极简、XML 分区、两级加载、注入真实状态、静态动态分开。++

++需求提示词管"你要做什么"——用 ## 分隔符把背景/任务/约束/参照物分区、给上下文不给教科书、给参照物比写规范有效、给约束和负面示例、复杂任务拆步骤。++

记住一个原则就够了：++模型知道怎么做，工具知道怎么管，你要做的是用结构化的方式把任务说清楚。++
