压缩会丢细节，要有一层不丢的：记忆系统

大家好，我是郑同学。又是"美好"的一周开始～

今天喝了瑞幸全冰奶酪美式，两口喝完，还有一杯子冰，不愧是全冰～

上一节 s08 读到结尾，作者留了个钩子：压缩让 Agent 能跑很久不会崩，但每次压缩后，用户之前告诉它的偏好、约束也跟着丢了。

我当时就想：是啊，s08 的 compact_history 会把对话压成摘要，"用 tab 缩进不要用空格"可能被简化成"用户有代码风格偏好"——偏好还在，但细节没了。更糟的是，新开一个会话，连摘要也没了。

s09 给出的答案特别直接——压缩会丢细节，要有一层不丢的。文件仓库 + 索引 + 按需加载，跨压缩、跨会话。

● ● ●

先看一眼"压缩丢偏好"是什么样

问题：压缩丢偏好

s08 的 autoCompact 会把当前目标、剩余工作、用户约束写进摘要——但细节会丢失。

举个具体场景：

用户: 以后写 Python 代码，用 tab 缩进，不用空格，单引号不要双引号
Agent: 好的，记住了
[Agent 跑了 30 分钟，上下文爆了，触发 compact]
[compact 摘要]: 用户有代码风格偏好
[下一轮] 用户: 帮我写个 utils.py
Agent: [用空格缩进，双引号] ← 偏好丢了

LLM 没有持久状态，所有信息都在上下文窗口里。上下文满了要压缩，压缩就有损。需要一层不参与压缩、跨会话保留的存储。

● ● ●

解决方案：文件仓库 + 索引 + 按需加载

方案：记忆系统架构

作者的思路是——把记忆存到文件系统，不放在上下文里。

存储选文件系统：.memory/ 目录下，每个记忆一个 .md 文件，带 YAML frontmatter（name / description / type）。文件多了需要索引：MEMORY.md 一行一个链接，注入 SYSTEM。

关键设计：索引常驻 SYSTEM prompt（可被 prompt cache 缓存），文件内容按需注入到当前 user turn（按 filename/description 匹配当前对话，不破坏 cache）。写入由每轮结束后的提取器完成。

什么是 prompt cache？ Anthropic 的 API 支持缓存——如果两次请求的 prompt 前缀完全一样，第二次只算新增部分的 token。SYSTEM 是每次请求的固定前缀，只要它不变，缓存就一直命中，省 token 又省时间。

为什么注入记忆不能进 SYSTEM？ 如果把相关记忆塞进 SYSTEM，每轮选的记忆不同，SYSTEM 就变了，缓存立刻失效——每轮都要重新算整个 SYSTEM 的 token。所以 s09 的设计是：索引常驻 SYSTEM（固定，可缓存），内容按需注入到 user turn（变动，但不影响 SYSTEM 缓存）。

四类记忆，各有用途：

类型回答什么示例
user你是谁"用 tab 不用空格"
feedback怎么做事"别 mock 数据库"
project正在发生什么"auth 重写是合规驱动"
reference东西在哪找"pipeline bug 在 Linear INGEST"

这四类覆盖了"以后还会用到什么"的主要场景。

● ● ●

存储：Markdown 文件 + 索引

每个记忆是一个 .md 文件，YAML frontmatter 记录元数据：

---
name: user-preference-tabs
description: User prefers tabs for indentation
type: user
---

User prefers using tabs, not spaces, for indentation.

**Why:** Consistency with existing codebase conventions.
**How to apply:** Always use tabs when writing or editing files.

MEMORY.md 是索引，一行一个链接：

- [user-preference-tabs](user-preference-tabs.md) — User prefers tabs for indentation

写入新记忆时自动重建索引：

def write_memory_file(name, mem_type, description, body):
    slug = name.lower().replace(" ", "-")
    filepath = MEMORY_DIR / f"{slug}.md"
    filepath.write_text(
        f"---\nname: {name}\ndescription: {description}\ntype: {mem_type}\n---\n\n{body}\n"
    )
    _rebuild_index()

为什么用 Markdown + YAML frontmatter？和 s07 的 SKILL.md 一模一样的结构——开头元数据，后面正文。这种结构可以被人直接读、被工具解析、被 LLM 理解。

读完这段我想起 s07——技能也是文件 + frontmatter，只是技能放在 skills/ 目录，记忆放在 .memory/ 目录。两个系统共享同一套文件格式，设计上高度一致。

● ● ●

加载：两条路径

路径一：索引常驻 SYSTEM

build_system() 在每次用户请求开始时读取 MEMORY.md，把记忆清单注入：

def build_system() -> str:
    index = read_memory_index()
    memories_section = f"\n\nMemories available:\n{index}" if index else ""
    return (
        f"You are a coding agent at {WORKDIR}."
        f"{memories_section}\n"
        "Relevant memories are injected below. Respect user preferences from memory.\n"
        "When the user says 'remember' or expresses a clear preference, extract it as a memory."
    )

索引常驻，但只是"清单"（name + description），不是完整内容。模型每轮都能看到"自己有什么记忆"，但要用的时候才加载详情。

路径二：相关记忆按需注入

每次用户请求开始时，load_memories() 把最近对话和记忆目录一起发给 LLM 做一次轻量 side-query，选出相关的文件名，再读文件内容临时注入到当前 user turn：

def select_relevant_memories(messages, max_items=5):
    files = list_memory_files()
    # Build catalog: "0: user-preference-tabs — User prefers tabs..."
    catalog = "\n".join(f"{i}: {f['name']} — {f['description']}" for i, f in enumerate(files))
    response = client.messages.create(
        model=MODEL,
        messages=[{"role": "user", "content":
            f"Select relevant memory indices. Return JSON array.\n\n"
            f"Recent conversation:\n{recent}\n\nMemory catalog:\n{catalog}"}],
        max_tokens=200
    )
    indices = json.loads(re.search(r'\[.*?\]', text).group())
    return [files[i]["filename"] for i in indices if 0 <= i < len(files)]

逐行读：

  •  把所有记忆的 name + description 列成清单。
  •  发给 LLM：根据最近对话，选出真正相关的记忆索引。
  •  LLM 返回 JSON 数组（如 [0, 3]）。
  •  按索引读文件内容注入。

最多 5 条，控制开销。如果 side-query 失败（API 错误、JSON 解析失败），降级到关键词匹配 name + description。

读到这里我停下来想了下——这个设计和 s07 的 skill 加载几乎一模一样：

  •  s07：SKILL_REGISTRY 是技能目录，load_skill 按需加载技能内容
  •  s09：MEMORY.md 是记忆目录，load_memories 按需加载记忆内容

两层目录 + 两级加载，一个是知识，一个是记忆。

● ● ●

写入：每轮结束后提取

用户不会每次都说"记住这个"。偏好通常散落在正常对话中——"用 tab 比空格好"、"以后都用单引号"。

extract_memories() 在每轮结束时运行，条件是模型停止且没有 tool_use（说明对话告一段落）：

# In agent_loop:
if response.stop_reason != "tool_use":
    extract_memories(pre_compress)  # 从压缩前快照提取新记忆
    consolidate_memories()           # 检查是否需要整理
    return

提取的 prompt：

def extract_memories(messages):

        "Return JSON array: [{name, type, description, body}].\n"
        "If nothing new or already covered, return [].\n\n"
        f"Existing memories:\n{existing}\n\nDialogue:\n{dialogue[:4000]}"
    )
    # ... parse response, write files ...

关键点：

  •  提取前先检查已有记忆，避免重复。
  •  只有确实有新信息时才写文件。
  •  从 pre_compress 快照提取——不是压缩后的 messages。

为什么要从压缩前快照提取？ 因为压缩会把对话压成摘要，细节已经丢了。从压缩前的完整对话提取，才能捕捉到用户说的"用 tab 不用空格"这种具体偏好。

整理：低频合并去重

记忆文件会积累。consolidate_memories() 在文件数达到阈值（默认 10）时触发，让 LLM 去重、合并矛盾、淘汰过时记忆：

原理讲完，贴出完整流程串一遍

核心流程：三个子系统

s09 的记忆系统就是三个子系统 + 一个存储格式：

[启动]
  read_memory_index() → SYSTEM 注入记忆清单
  load_memories() → LLM 选相关记忆 → 注入当前 user turn

[对话中]
  用户请求 → LLM 处理 → 工具执行 → ...
  （和 s08 的压缩管线并行）

[每轮结束]
  extract_memories() → 从压缩前快照提取新记忆
  consolidate_memories() → 文件数 ≥ 10 时合并去重

三个子系统：

  •  加载（load）：索引常驻 SYSTEM + 相关记忆按需注入
  •  提取（extract）：每轮结束后从对话里挖新记忆
  •  整理（consolidate）：低频合并去重

加载是"读"，提取是"写"，整理是"维护"。三个子系统配合，让记忆系统始终保持最新、最相关、不冗余。

一次完整的记忆流转

[第 1 轮] 用户: "用 tab 缩进，不用空格，记住"
  → Agent 回答 + extract_memories 提取
  → 写入 user-preference-tabs.md
  → MEMORY.md 索引更新

[第 2 轮] 用户: "帮我写个 utils.py"
  → SYSTEM 里已有索引（user-preference-tabs 可见）
  → load_memories 选出 user-preference-tabs（匹配 Python 代码请求）
  → 记忆内容注入当前 user turn
  → Agent 用 tab 缩进写 utils.py ✅

[新会话] 用户重新打开 Agent
  → SYSTEM 重建时读取 MEMORY.md
  → 上一会话的偏好还在
  → Agent 记得"用 tab"

跨压缩、跨会话——这就是记忆系统的威力。

对比真实 Claude Code

维度对照表：教学版 vs CC

教学版的记忆系统已经很完整了，但读到"深入 CC 源码"那节，真实 CC 考虑更多：

维度教学版Claude Code
记忆选择LLM side-query + 关键词降级Sonnet side-query（无降级，findRelevantMemories.ts）
提取时机stop_reason != "tool_use" 分支stop hook（stopHooks.ts:141-155）
提取执行直接调用forked agent，受限权限，maxTurns: 5
文件上限无200 行 / 25KB（MEMORY.md），200 行 / 4096 字节（单文件）
Dream 整理文件数 ≥ 10四层门控（时间/扫描/会话/锁）
存储位置.memory/~/.claude/projects//memory/
Session Memory无有（session-memory//memory.md）

几个让我印象深刻的差距：

记忆选择：LLM 选，不是 embedding。CC 用 Sonnet 本身来选，不是 embedding 向量相似度。为什么？因为记忆的"相关性"不是字面相似，而是语义相关性——"用 tab 缩进"和"写 Python 文件"字面不相似，但语义相关。LLM 比向量更懂这种关联。

提取通过 forked agent 执行。CC 不是直接调 LLM 提取记忆，而是派一个子 Agent（接 s06 的 subagent），给它受限权限、skipTranscript: true、maxTurns: 5。子 Agent 隔离执行，不会污染主对话。还有重叠保护：如果主 Agent 已经写入了记忆文件，跳过提取。

Dream：四层门控，不是数量阈值。CC 不是"文件数够了就合并"，而是四层门控：

  1. 01时间门控：距上次合并 ≥ 24 小时
  3. 02扫描节流：避免频繁扫描文件系统
  5. 03会话门控：自上次合并以来修改了 ≥ 5 个会话 transcript[记录]
  7. 04锁门控：没有其他进程正在合并（.consolidate-lock 文件）

合并本身也通过 forked agent 执行。锁文件 mtime 就是 lastConsolidatedAt。崩溃恢复：1 小时后锁自动过期。

User Memory vs Session Memory。CC 还区分两种记忆：

User MemorySession Memory
持久性跨会话单会话
存储memory/ 下多个 .md 文件session-memory//memory.md
加载到system promptcompact 摘要
用途跨会话的知识积累跨 compact 的上下文连续性

sessionMemoryCompact（s08 提到的机制）正是用了 Session Memory：autoCompact 前先读 session memory 文件，如果内容足够（≥ 10K token、≥ 5 条文本消息、≤ 40K token），就用它做摘要，直接复用会话过程已提取好的结构化记忆，不调 LLM。这就是 s08 对比表里那个"辅助机制"的真身。

教学版的简化是刻意的——四层门控简化成文件数阈值、forked agent 简化成直接调用、session memory 完全省略。先把"存储 + 加载 + 提取 + 整理"这个核心讲清楚，生产级的复杂性后面再展开。

● ● ●

一个容易忽略的细节：从压缩前快照提取

读代码时我注意到一个细节——extract_memories 是从 pre_compress 快照提取，不是从压缩后的 messages：

# In agent_loop:
pre_compress = [m if isinstance(m, dict) else {...} for m in messages]
# s08: compression pipeline
messages[:] = tool_result_budget(messages)
messages[:] = snip_compact(messages)
messages[:] = micro_compact(messages)
if estimate_size(messages) > CONTEXT_LIMIT:
    messages[:] = compact_history(messages)
# ... LLM 调用 ...
if response.stop_reason != "tool_use":
    extract_memories(pre_compress)  # ← 从压缩前快照！

这个细节很关键。压缩后的 messages 可能已经被 L2/L3/L4 处理过——旧 tool_result 被占位、大结果落盘、对话被摘要。如果从压缩后的 messages 提取记忆，细节已经丢了。

从压缩前快照提取，才能捕捉到用户说的"用 tab 不用空格"这种具体偏好。

读到这儿我想起 s08 的教训——压缩是信息降级，记忆要抢在降级前把重要的捞出来。s09 的 extract_memores 就是这个"捞"的动作。

小结

读完 s09，我自己最大的感悟是——记忆系统让 Agent 有了"连续性"。

s08 的压缩是"短期记忆"——当前会话内的腾挪。s09 的记忆系统是"长期记忆"——跨压缩、跨会话的知识积累。

四个关键设计：

  1. 01存储文件系统：.memory/ 下每个记忆一个 .md，YAML frontmatter 记元数据
  3. 02索引常驻 SYSTEM：MEMORY.md 一行一个链接，模型每轮都看到清单
  5. 03相关记忆按需注入：LLM side-query 选相关记忆，最多 5 条
  7. 04每轮结束提取：从压缩前快照挖新记忆，低频整理去重

几个关键点回顾：

  1. 01s09 加了记忆系统：write_memory_file / select_relevant_memories / load_memories / extract_memories / consolidate_memories
  3. 02四类记忆：user（你是谁）/ feedback（怎么做事）/ project（正在发生什么）/ reference（东西在哪找）
  5. 03记忆选择用 LLM，不是 embedding——语义相关性比字面相似更准
  7. 04提取从压缩前快照——细节还没丢
  9. 05真实 CC 有 forked agent 隔离、四层门控 Dream、Session Memory 等更精细机制

记忆系统的本质是"给 Agent 加一层不参与压缩的存储"——让重要的东西跨压缩、跨会话保留下来。
