用到时才加载：给AI一张按需知识卡片

大家好，我是郑同学。周末赶紧多学学[旺柴]

上一节 s06 读到结尾，作者留了个钩子：Agent 现在能拆任务了，但每个任务需要的知识不一样——改前端组件需要 React 规范，写 SQL 需要表结构。这些知识全塞进 system prompt，上下文直接爆掉。

我当时就想：是啊，前几节的 SYSTEM 就是几行固定字符串，还好。要是真把项目文档塞进去——React 规范 2000 行、SQL 指南 1500 行、API 设计 3000 行——每次调 LLM 都带着 6500 行文档，改个 CSS 颜色也得读一遍 SQL 规范，99% 的内容跟当前任务无关。

s07 给出的答案特别精妙——两层加载。这一节就读这个。

● ● ●

先看一眼"全塞进 system prompt"的灾难

问题：全塞prompt的灾难

作者在 README 里给的例子：

SYSTEM = (
    f"You are a coding agent. "
    + open("docs/react-style.md").read()   # 2000 行
    + open("docs/sql-style.md").read()     # 1500 行
    + open("docs/api-design.md").read()    # 3000 行
)

读到这儿我算了一下：6500 行 system prompt，每轮 LLM 调用都带着。Agent 改一个按钮颜色，也得在上下文里驮着 SQL 风格指南。token 烧得没意义，注意力也被稀释。

更糟的是——这些文档还会变。React 规范更新一版，整个 SYSTEM 就得重拼。文档一多，system prompt 就变成一个永远在膨胀的怪物。

● ● ●

解决方案：两层加载

方案：两级加载

作者的思路是——把"知道有这个技能"和"会用这个技能"分开。

具体做法分两层：

层位置时机代价
**1. 目录**system prompt启动时注入~100 tokens/skill，每轮都带
**2. 内容**tool_resultAgent 调 load_skill 时~2000 tokens/skill，按需

第一层便宜，每轮都带——只告诉模型"有这些技能可用"，每个技能一行描述。模型永远知道自己手里有什么牌。

第二层贵，用到才加载——模型决定"我现在要写 SQL"，调一下 load_skill("sql-style")，完整的 1500 行 SQL 规范才进入上下文。改 CSS 颜色的时候，SQL 规范一个字都不占位置。

● ● ●

skills/ 目录：技能的家

每个技能是一个子目录，里面有一个 SKILL.md 文件：

skills/
├── agent-builder/SKILL.md
├── code-review/SKILL.md
├── mcp-builder/SKILL.md
└── pdf/SKILL.md

每个 SKILL.md 是一个带 YAML frontmatter 的 Markdown 文件——开头是元数据（name、description），后面是完整内容。这种结构和 Hexo/Jekyll 的文章头很像，一眼能看懂。

● ● ●

第一层：启动时扫描，注入目录

看下启动时怎么扫描：

SKILL_REGISTRY: dict[str, dict] = {}

def _scan_skills():
    """启动时扫描 skills/ 目录，把每个技能的元数据存进注册表"""
    if not SKILLS_DIR.exists():
        return
    for d in sorted(SKILLS_DIR.iterdir()):
        if not d.is_dir():
            continue
        manifest = d / "SKILL.md"
        if manifest.exists():
            raw = manifest.read_text()
            meta, body = _parse_frontmatter(raw)
            name = meta.get("name", d.name)
            desc = meta.get("description", raw.split("\n")[0].lstrip("#").strip())
            SKILL_REGISTRY[name] = {"name": name, "description": desc, "content": raw}

_scan_skills()  # 启动时跑一次

逐行读：

  •  SKILL_REGISTRY 是个全局字典，这就是"技能注册表"。
  •  遍历 skills/ 下的每个子目录，找 SKILL.md。
  •  _parse_frontmatter 解析 YAML 头，拿到 name 和 description。
  •  注意：content 字段存的是整个文件原文，不只是元数据。这个细节第二层会用到。
  •  _scan_skills() 启动时调用一次，之后注册表就固定了。

然后 build_system() 把注册表格式化成目录，塞进 SYSTEM：

def list_skills() -> str:
    return "\n".join(f"- **{s['name']}**: {s['description']}" for s in SKILL_REGISTRY.values())

def build_system() -> str:
    catalog = list_skills()
    return (
        f"You are a coding agent at {WORKDIR}. "
        f"Skills available:\n{catalog}\n"
        "Use load_skill to get full details when needed."
    )

SYSTEM = build_system()

最终 SYSTEM 长这样：

You are a coding agent at /path/to/project.
Skills available:
- **agent-builder**: Build agent harness step by step
- **code-review**: Review code against team conventions
- **mcp-builder**: Create MCP server scaffold
- **pdf**: Extract and process PDF content
Use load_skill to get full details when needed.

4 个技能，每个一行描述，总共也就 100 来个 token。模型每轮都能看到自己有什么牌，几乎不花成本。

● ● ●

第二层：load_skill 按需加载完整内容

Agent 决定要用某个技能了，调 load_skill：

def load_skill(name: str) -> str:
    """加载技能完整内容。通过注册表查找，没有路径遍历风险。"""
    skill = SKILL_REGISTRY.get(name)
    if not skill:
        return f"Skill not found: {name}"
    return skill["content"]

就这 4 行。

逐行读：

  •  参数 name 是技能名（比如 "code-review"）。
  •  从 SKILL_REGISTRY 查找，不是从文件路径读。这个区别很关键——没有路径遍历风险，模型不能通过 load_skill("../../../etc/passwd") 读系统文件。
  •  找不到返回 "Skill not found"。
  •  找到了返回 skill["content"]——完整的 SKILL.md 内容。

这个内容不是进入 SYSTEM，而是作为 tool_result 进入当前 messages。这是和"全塞 system prompt"最本质的区别——技能内容是一次工具调用的结果，会随着对话历史一起被携带，但不是每轮强制携带。上下文压缩、截断、会话结束，它都会自然消失。

● ● ●

原理讲完，贴出完整核心代码串一遍

原理讲完了，但在跑 Demo 之前，我想把 s07 的核心代码完整贴出来，把"两级加载"是怎么配合的串一遍。

完整核心就三块：扫描器 + 目录构建器 + 加载器。

# === 第一块：启动时扫描器 ===
SKILL_REGISTRY: dict[str, dict] = {}

def _scan_skills():
    """启动时扫描 skills/ 目录，填充注册表"""
    if not SKILLS_DIR.exists():
        return
    for d in sorted(SKILLS_DIR.iterdir()):
        if not d.is_dir():
            continue
        manifest = d / "SKILL.md"
        if manifest.exists():
            raw = manifest.read_text()
            meta, body = _parse_frontmatter(raw)
            name = meta.get("name", d.name)
            desc = meta.get("description", ...)
            SKILL_REGISTRY[name] = {"name": name, "description": desc, "content": raw}

_scan_skills()  # 启动时跑一次，之后注册表固定

# === 第二块：目录构建器（注入 SYSTEM） ===
def list_skills() -> str:
    """把注册表格式化成目录"""
    return "\n".join(f"- **{s['name']}**: {s['description']}" for s in SKILL_REGISTRY.values())

def build_system() -> str:
    """构建 SYSTEM，技能目录注入"""
    catalog = list_skills()
    return (
        f"You are a coding agent at {WORKDIR}. "
        f"Skills available:\n{catalog}\n"
        "Use load_skill to get full details when needed."
    )

SYSTEM = build_system()  # 启动时构建一次

# === 第三块：加载器（运行时按需调用） ===
def load_skill(name: str) -> str:
    """运行时加载完整内容。注册表查找，无路径遍历风险。"""
    skill = SKILL_REGISTRY.get(name)
    if not skill:
        return f"Skill not found: {name}"
    return skill["content"]

# 挂到工具表
TOOL_HANDLERS["load_skill"] = load_skill

三块各自独立，但配合起来就是完整的两级加载。串一遍：

第一块——扫描器。启动时跑一次，遍历 skills/ 目录，把每个 SKILL.md 的元数据（name、description）和完整内容（content）都存进注册表。之后注册表只读，不再变。

第二块——目录构建器。把注册表格式化成"技能列表"，注入 SYSTEM。每轮 LLM 调用都带着这个目录，模型永远知道自己有什么牌。成本极低（~100 tokens）。

第三块——加载器。模型决定用某个技能时，调 load_skill("xxx")。通过注册表查找（不是文件路径），返回完整 content。这个内容作为 tool_result 进入 messages，不是进入 SYSTEM。

一次完整的调用流程

[启动]
  _scan_skills() → 注册表填充 4 个技能
  build_system() → SYSTEM = "...Skills available: agent-builder, code-review..."

[用户提问]"帮我做代码评审"
  → LLM 看 SYSTEM 目录，发现 code-review 技能
  → 决定调用：load_skill("code-review")
  → load_skill 返回完整 SKILL.md 内容（~2000 tokens）
  → 内容作为 tool_result 进入 messages
  → LLM 后续按这个规范做评审

[另一个用户提问]"改个按钮颜色"
  → LLM 看 SYSTEM 目录，发现没有相关技能
  → 直接用 edit_file 改，不调 load_skill
  → SQL 规范、API 文档 一个 token 都不占

看这个流程：第一层目录始终在，第二层内容按需来。这就是两级加载的威力。

对比真实 Claude Code

对比真实CC：多来源

教学版的两级加载已经很巧妙了，但读到"深入 CC 源码"那节，我才发现真实 CC 走得更远。技能来源不是一个目录，是好多个：

几个让我印象深刻的差距：

技能来源多样。CC 不只从 skills/ 加载，还有：

  •  user skills（~/.claude/skills/，用户全局）
  •  project skills（.claude/skills/，项目级）
  •  bundled skills（内置技能）
  •  MCP skills（远程技能）
  •  legacy commands（.claude/commands/，老格式）
  •  conditional skills（带 paths frontmatter，按文件路径激活）

教学版只有一个目录，概念清晰但简化了。

frontmatter 字段丰富。CC 的 SKILL.md 可以声明：

  •  when_to_use——告诉模型什么时候调
  •  allowed-tools——这个技能允许用哪些工具
  •  context: 'fork'——作为子 Agent 运行（和 s06 衔接）
  •  model——指定用哪个模型（haiku/sonnet/opus）
  •  hooks——技能级别的 hook 配置
  •  paths——条件激活（比如只在 *.tsx 文件下激活 React 技能）

教学版只解析 name 和 description，把复杂度藏起来了。

两级加载的精确实现。CC 的 Catalog 阶段有预算限制——上下文窗口的 ~1%，上限 8000 字符。超了就截断，不会让技能目录无限膨胀。

Load 阶段的实现更值得细看。教学版的 load_skill 是"打包塞"——直接 return skill["content"]，把完整 SKILL.md（~2000 tokens）整个塞进 tool_result。

CC 的 Skill 工具是"分两份塞"：

# 教学版：tool_result 直接是完整内容
tool_result = {
    "content": "# 完整 SKILL.md 全文（~2000 tokens）..."
}

# CC：tool_result 只是一句提示，真正内容在另一条 message
tool_result = {
    "content": "Launching skill: code-review"  # ← 只有 ~20 tokens
}
# 同时往对话里追加一条独立 message（newMessages）
messages.append({
    "role": "user",
    "content": "# 完整 SKILL.md 全文（~2000 tokens）..."
})

这个"拆分"看着不起眼，但精细在哪？ 三点：

第一，上下文压缩策略能区别对待。 tool_result 是"被压缩的目标"（s08 会讲），大块内容单独存成 message，压缩策略可以独立选择保留还是丢弃。教学版全塞 tool_result 里，压缩时一刀切——要么留要么删，没法精细控制。

第二，支持 forked skills。 当技能声明 context: 'fork'（作为子 Agent 运行），技能内容需要作为独立 message 传给子 Agent 的全新 messages[]（s06 的 subagent）。CC 的拆分天然支持这个——直接把那条 message 复制过去就行。教学版的 tool_result 就做不到。

第三，UI 流式渲染。 用户看到的是 tool_result 的"Launching skill: xxx"，UI 可以先显示"正在加载..."，然后才把技能内容渐进式渲染。教学版直接 return 全文，UI 只能等完整结果出来一次性展示。

教学版的简化是刻意的——把 tool_result 和 newMessages 合并成"直接 return 全文"，概念清晰，先讲明白"按需加载"这个核心。CC 的拆分是为了生产级的可控性，复杂度藏起来了。

● ● ●

一个容易忽略的细节：注册表查找防路径遍历

安全细节：防路径遍历

读代码时我注意到一个细节——load_skill 是从注册表查找，不是从文件路径读：

def load_skill(name: str) -> str:
    skill = SKILL_REGISTRY.get(name)  # ← 字典查找
    if not skill:
        return f"Skill not found: {name}"
    return skill["content"]

这个区别很关键。如果是 open(f"skills/{name}/SKILL.md").read()，模型可以传 "../../../etc/passwd" 读系统文件——路径遍历攻击。

但从字典查找就没事——注册表里有什么 key，就只能查什么 key。模型传 "../../../etc/passwd"，字典里没这个 key，直接返回 "Skill not found"。

读到这儿我想起 s03 的结论：安全要靠代码强制。s07 把这个原则贯彻到了技能加载——哪怕模型再聪明，也不能绕过注册表读外部文件。

● ● ●

小结

读完 s07，我自己最大的感悟是——知识也是资源，需要按需分配。

前几节 Agent 的"知识"全在 SYSTEM 里——就那几行固定字符串，还好。但真实项目里，知识是海量的——React 规范、SQL 指南、API 文档、团队约定……全塞 SYSTEM 就是灾难。

s07 给出的答案是两级加载：

  •  第一层（目录）始终在——每轮 ~100 tokens，模型永远知道自己有什么牌
  •  第二层（内容）按需来——用到才调 load_skill，不用就一个字都不占

几个关键点回顾：

  1. 01s07 加了一个 load_skill 工具——按需加载技能完整内容
  3. 02两级设计：++启动时扫描注入 SYSTEM（便宜） + 运行时 load_skill 加载内容（贵但按需）++
  5. 03技能存在 skills/ 目录，每个技能一个 SKILL.md（YAML frontmatter + Markdown）
  7. 04load_skill 从注册表查找，防路径遍历攻击
  9. 05真实 CC 有多来源（user/project/bundled/MCP/legacy）、多字段 frontmatter、forked skills、条件激活

load_skill 本身没给 Agent 增加任何执行能力，但它让 Agent 有了"知识获取"这个维度。 模型自己判断什么时候需要什么知识，主动去拿。这是我读这章最大的收获。
