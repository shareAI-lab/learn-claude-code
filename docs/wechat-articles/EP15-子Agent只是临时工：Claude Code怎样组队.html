子Agent只是临时工：Claude Code怎样组队

我原来一直把“开三个子 Agent”理解成“组了一个团队”。读到 s15 才发现，这更像同时叫了三份外卖：每个人领一个需求，交付一份总结，然后关系结束。

真正的队友得能被再次找到。你做到一半可以补一句“字段改成 UUID”，Alice 做完也能主动回一句“schema 已写好”。没有来回通信，再多模型也只是各干各的。

前一节 s14 让 AI 到点自己开工；但遇到大项目——认证、数据库、API、测试同时要改——一份上下文塞不下。s15 开始把"叫外卖"改造成"带团队"。

我不从“多 Agent”这个大词讲起，直接看两个文件：alice.jsonl 和 lead.jsonl。团队成立的第一步不是多开模型，而是让每个模型有名字、有自己的记忆、也有一个能收信的邮箱。

● ● ●

s06 的子 Agent，为什么还不是队友

s06 的 subagent 就像叫外卖：你下单，它跑一趟，送回来就走了。它能省主对话空间，但沟通只有一去一回。

s15 把关系拉长了：你启动 Alice 后还能继续给她发消息（"字段改一下"），Alice 干活时能主动汇报（"建到一半发现缺依赖"），结束时还会自动发一条总结。这才像同事。

子Agent不是队友

● ● ●

给每个 Agent 一个文件邮箱

教学版的消息总线特别朴素：每个 AI 有一个"邮箱"，其实就是 .mailboxes/ 目录下的一个小文件。发消息就是往文件里追加一行，读消息就是读完删掉。

就像公司里的纸质信箱：你塞一封信进去，对方来取走，信箱就空了。

# 收件箱目录
MAILBOX_DIR = WORKDIR / ".mailboxes"
# 不存在就创建
MAILBOX_DIR.mkdir(exist_ok=True)


# 消息总线：所有 AI 共用这一个实例
class MessageBus:
    """File-based message bus. Each agent has a .jsonl inbox.
    Read is destructive: read_text + unlink (consumes messages).
    Teaching version: no file locking; real CC uses proper-lockfile."""

    # 发送者、接收者、内容
    def send(self, from_agent: str, to_agent: str, content: str,
             msg_type: str = "message"):
        # 构造消息字典：谁发给谁
        msg = {"from": from_agent, "to": to_agent,
               "content": content, "type": msg_type,
               "ts": time.time()}
        # 按接收者命名文件，如 alice.jsonl
        inbox = MAILBOX_DIR / f"{to_agent}.jsonl"
        # 追加模式，不覆盖旧消息
        with open(inbox, "a") as f:
            f.write(json.dumps(msg) + "\n")
        print(f"  \033[33m[bus] {from_agent} → {to_agent}: "
              f"{content[:50]}\033[0m")

    # 读取某人的全部信件
    def read_inbox(self, agent: str) -> list[dict]:
        inbox = MAILBOX_DIR / f"{agent}.jsonl"
        # 文件不存在说明邮箱为空
        if not inbox.exists():
            return []
        # 逐行还原消息
        msgs = [json.loads(line) for line in inbox.read_text().splitlines()
                if line.strip()]
        # 消费式读取：读完删除文件
        inbox.unlink()
        return msgs

文件不是为了高性能，而是为了简单可见。打开目录就能看到消息，线程之间也能共享；进程崩溃前已经落盘的未读消息仍可能保留。

给每个AI一个邮箱

● ● ●

启动队友：不是复制一段对话，而是新开一条循环

你通过 spawn_teammate 工具创建队友。先处理身份和重名：

# 记录当前存活的队友
active_teammates: dict[str, bool] = {}


def spawn_teammate_thread(name: str, role: str, prompt: str) -> str:
    """Spawn a teammate agent in a background thread.
    Teaching version: max 10 rounds per teammate.
    Real CC: teammates use idle loop (wait for inbox, work, repeat)
    until shutdown_request."""
    # 同名队友已存在，拒绝重复创建
    if name in active_teammates:
        return f"Teammate '{name}' already exists"

    # 拼接 system prompt，写入身份和角色
    system = (f"You are '{name}', a {role}. "
              f"Use tools to complete tasks. "
              f"Send results via send_message to 'lead'.")

active_teammates 防止同一进程里同时创建两个 Alice。system 把名字、角色和汇报对象写清楚——所以 Alice 知道自己是"backend dev"，也知道结果要发给"lead"。

队友不是把你的聊天记录复制一份。Alice 从自己的初始任务开始，有自己独立的对话历史：

def run():
    # 从初始任务开始，不带 Lead 的历史
    messages = [{"role": "user", "content": prompt}]
    sub_tools = [
        {"name": "bash", "description": "Run a shell command.", ...},
        {"name": "read_file", "description": "Read file contents.", ...},
        {"name": "write_file", "description": "Write content to a file.", ...},
        # 队友独有的通信工具
        {"name": "send_message",
         "description": "Send a message to another agent.", ...},
    ]
    # 工具名 → 处理函数的映射
    sub_handlers = {
        "bash": run_bash, "read_file": run_read, "write_file": run_write,
        # 发消息走总线
        "send_message": lambda to, content: (BUS.send(name, to, content),
                                              "Sent")[1],
    }

这里有两层限制：

  •  Alice 的对话从她自己的初始任务开始，不带你的完整聊天记录。这样她不会被无关内容干扰。
  •  Alice 只有 bash、read_file、write_file、send_message 四个工具。她能干活和汇报，但不能继续创建队友，也不能管理定时任务。

这不是“能力越少越高级”，而是像公司里的分工：项目经理负责分配任务，程序员负责写代码和汇报进度。

● ● ●

队友每一轮先收信，再决定下一步

队友循环的实际顺序是：先看邮箱，再调模型，再执行工具。

# 最多跑 10 轮，防止无限循环
for _ in range(10):
    # 每轮开头先收信
    inbox = BUS.read_inbox(name)
    # 有新消息才注入
    if inbox:
        # 把收到的消息注入对话
        messages.append({"role": "user",
                         "content": f"<inbox>{json.dumps(inbox)}</inbox>"})
    try:
        # 只传最近 20 条，控制上下文长度
        response = client.messages.create(
            model=MODEL, system=system, messages=messages[-20:],
            tools=sub_tools, max_tokens=8000)
    except Exception:
        # API 出错就直接退出
        break
    # 记录模型回复
    messages.append({"role": "assistant", "content": response.content})
    # 没有工具调用 → 任务完成，退出循环
    if response.stop_reason != "tool_use":
        break
    results = []
    # 遍历所有工具调用
    for block in response.content:
        if block.type == "tool_use":
            # 查工具处理函数
            handler = sub_handlers.get(block.name)
            output = handler(**block.input) if handler else "Unknown"
            # 按原 ID 回 tool_result
            results.append({"type": "tool_result",
                            "tool_use_id": block.id,
                            "content": str(output)})
    # 工具结果追加到对话
    messages.append({"role": "user", "content": results})

所谓“收件箱注入”，就是把邮箱里读到的消息追加到队友的 messages，让她下一次调用模型时看见。

这里我读到一个和标题有点冲突的事实：s15 的“持久队友”只是相对 s06 更持久。教学版队友一旦返回普通文本就退出，并不会真的长期 idle 等待下一封信。

队友有自己的脑子

● ● ●

做完以后，结果怎样回到 Lead

队友可能在执行中主动调用 send_message。即使没主动发，线程退出前也会从最后几条 assistant 消息里找一段文字，自动发送总结：

# 退出前自动汇报
# Send final summary to Lead
summary = "Done."
# 从后往前找最新的 assistant 文本
for msg in reversed(messages):
    if msg["role"] == "assistant" and isinstance(msg["content"], list):
        for b in msg["content"]:
            if getattr(b, "type", None) == "text":
                # 取到第一段文本作为总结
                summary = b.text
                break
        else:
            continue
        break
# 发送给 Lead，类型标记为 result
BUS.send(name, "lead", summary, "result")
# 移除活动标记，允许同名重建
active_teammates.pop(name, None)
print(f"  \033[32m[teammate] {name} finished\033[0m")

它从后往前找最新 assistant 文本；找不到就使用 Done.。先发总结再移除活动标记，保证正常退出时 Lead 不会只看到“队友消失”而收不到结果。

Lead 的手动工具也很简单：

# Lead 专用：给队友发消息
def run_send_message(to: str, content: str) -> str:
    # 发送者固定为 lead
    BUS.send("lead", to, content)
    return f"Sent to {to}"


# Lead 专用：查收队友汇报
def run_check_inbox() -> str:
    # 消费 Lead 的邮箱
    msgs = BUS.read_inbox("lead")
    # 邮箱为空
    if not msgs:
        return "(inbox empty)"
    lines = []
    for m in msgs:
        # 每条截到 200 字，防止太长
        lines.append(f"  [{m['from']}] {m['content'][:200]}")
    return "\n".join(lines)

CLI 主循环每轮结束后还会自动检查 Lead 邮箱：

# CLI 每轮结束后自动检查 Lead 邮箱
inbox = BUS.read_inbox("lead")
# 有未读消息才处理
if inbox:
    # 格式化每条消息
    inbox_text = "\n".join(
        f"From {m['from']}: {m['content'][:200]}" for m in inbox)
    # 包装成 user 消息追加到历史
    history.append({"role": "user",
                    "content": f"[Inbox]\n{inbox_text}"})
    print(f"\n\033[33m[Inbox: {len(inbox)} messages injected]\033[0m")

它把结果包装成 [Inbox]，追加到 Lead 的 history。打印消息不等于模型知道消息；只有进入 history，下一轮 Lead 才能据此决策。

这条链里有两份完全不同的历史：Alice 的 messages 和 Lead 的 history。消息总线不共享整个上下文，只传递双方明确发出的那几条信息。

团队协作不是把所有人的聊天拼成一锅，而是在隔离上下文之间建立可追踪的消息通道。

● ● ●

Demo：跑一遍看邮箱怎么收发

光看代码没感觉，跑一下。

先创建一个队友 Alice，给她派活：

s15 >> Spawn alice and ask her to report schema result
[teammate] alice spawned as backend dev
  [bus] lead → alice: Create schema.sql

第一行是探针输入。第二行说明 Alice 的线程已经启动，名字和角色都写进了 active_teammates。第三行 MessageBus.send() 打印——Lead 往 .mailboxes/alice.jsonl 追加了一条消息。注意这只是一行 JSON，不是 RPC 调用，Alice 不需要马上响应。

Alice 读完信，邮箱就空了：

alice inbox: [{'from': 'lead', 'to': 'alice', 'content': 'Create schema.sql', ...}]

read_inbox("alice") 读完直接删文件，所以这条消息不会在下一次检查时重复出现。这就是"消费式收件箱"——读完即删。

Alice 干完活，往回写：

  [bus] alice → lead: Schema done: users(id, name)

方向反过来了，但用的是同一个 send()。消息落在 .mailboxes/lead.jsonl，不是直接写进 Lead 的聊天历史。

Lead 怎么收到？

[Inbox]
From alice: Schema done: users(id, name)
lead.jsonl exists after consume: False

Lead 读自己的邮箱，把消息格式化成 [Inbox] From alice: ... 加到 messages 里。最后一行验证了读完后 lead.jsonl 真的没了——消费完就删，不会堆积。

一句话：发消息就是往文件追加一行，读消息就是读完删掉文件。没有数据库、没有消息队列，只有 JSONL 文件和一把锁。

真实团队还差什么

● ● ●

源码边界：邮箱能通信，还不能保证不丢信

教学版把核心机制做出来了，但实际代码有几条很硬的边界。

第一，无锁读取会丢消息。 read_inbox() 先 read_text()，再 unlink()。如果另一个线程刚好在两步之间 append，新消息可能跟旧文件一起被删除。这不是理论问题，而是明确的 read-delete 竞态。

第二，队友不是长期在线。 模型一旦返回非 tool_use，循环马上 break；线程结束后 active_teammates.pop()。之后再往 alice.jsonl 发消息，不会有活着的 Alice 来读。

第三，异常会留下幽灵队友。 except Exception: break 还能走到最后清理；但 run() 里如果某个 handler 抛出未捕获异常，可能跳过 active_teammates.pop()，之后同名队友无法重建。

第四，共享同一个 WORKDIR。 Alice 和 Bob 虽然上下文独立，文件目录却没有隔离。两个队友同时改 schema.sql，仍可能互相覆盖。通信解决协作，不解决文件写冲突；真正隔离要等 s18 的 Git worktree。

第五，Lead 的自动收信不会主动拉起模型。 当前 CLI 在一次用户输入处理完后检查 inbox；如果 Alice 稍后才完成，Lead 要等下一次外部循环。真实 CC 的 useInboxPoller 才会每秒检查并提交新 turn。

s15 证明“队友 + 邮箱”能跑通最小闭环，但可靠团队还需要锁、空闲唤醒、关机协议和工作目录隔离。

● ● ●

小结

读完 s15，我不再把“同时调用多个模型”直接叫团队。并发只是一起开工，团队还要知道彼此是谁、怎样传消息、结果交给谁。

教学版用两类状态把这件事讲透了：独立的 teammate messages 保存各自思考过程，.mailboxes/*.jsonl 只传需要共享的信息。上下文保持隔离，协作通过消息发生。

感兴趣可以 clone 源码，开两个终端盯着 .mailboxes/：看 alice.jsonl 被写入、消费、删除，再看 lead.jsonl 走同一遍过程。

下一节 s16 会从一个很具体的问题继续：Lead 发“关机”后，不能直接杀线程；Alice 还可能写文件。请求和回复需要 request_id，关机需要一套能确认、能拒绝、不会配错人的握手。
