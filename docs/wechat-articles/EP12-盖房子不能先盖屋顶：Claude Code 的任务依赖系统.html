盖房子不能先盖屋顶：Claude Code 的任务依赖系统

大家好，我是郑同学。疯狂星期四，继续肝[旺柴]

上一节 s11 结尾：Agent 现在能在错误中自动恢复了，但它处理的任务仍然是"一次性"的。你给它一个任务，它做完，结束。

我当时就想：真正干活的时候，一个项目哪是一个任务？搭数据库、写 API、加测试、写文档——这些任务有先后顺序，盖房子不能先盖屋顶再打地基。

s05 的 TodoWrite 是个列表，没有依赖关系、没有持久化、对话结束就没了。s12 给出的答案是——任务不是清单，是图。有依赖、有状态、持久化到磁盘。

● ● ●

先看一眼 TodoWrite 为什么不够用

便利贴vs项目管理工具

s05 的 TodoWrite 是这样的：

□ 搭数据库 schema
□ 写 API 接口
□ 写测试
□ 写文档

四个 checkbox。问题是：Agent 可能先写 API，写到一半发现没数据库表，回头补；加测试时发现 API 接口签名又变了……

列表没有顺序约束。四个任务看起来平等的排在那儿，Agent 哪个先做全凭模型心情。而且对话一结束，列表就没了——下次开新会话，Agent 不知道之前做了什么。

TodoWrite (s05)Task System (s12)
存储内存列表.tasks/ JSON 文件
依赖无blockedBy 依赖图
持久性对话结束即丢跨会话
多 Agent无owner 字段
状态checked / uncheckedpending → in_progress → completed

TodoWrite 是便利贴，Task System 是项目管理工具。

● ● ●

Task 数据结构：一个任务就是一个文件

每个任务是一个 JSON 文件，存在 .tasks/ 目录：

@dataclass
class Task:
    id: str              # task_1700000000_a3f2
    subject: str         # "搭建数据库 schema"
    description: str     # 详细描述
    status: str          # pending | in_progress | completed
    owner: str | None    # 谁在做（多 Agent 场景）
    blockedBy: list[str] # 依赖的任务 ID 列表

ID 用 timestamp + random hex 生成，简单但够用。CC 用顺序 ID + highwatermark 文件防止 ID 重用。

为什么每个任务单独一个文件？ 因为文件系统是天然的并发安全存储——++多个 Agent 可以同时操作 .tasks/ 目录，不会互相覆盖整个列表==。如果全放一个文件，多 Agent 同时写就炸了。

● ● ●

核心机制：blockedBy 依赖检查

盖房子不能先盖屋顶

任务之间有先后。blockedBy 声明依赖——"写 API" 的 blockedBy 是 ["task_schema"]，意思是 schema 没做完之前，API 任务不能开始。

can_start 是认领的前置检查：

def can_start(task_id: str) -> bool:
    task = load_task(task_id)
    for dep_id in task.blockedBy:
        if not _task_path(dep_id).exists():
            return False  # 依赖不存在 = 被阻塞
        if load_task(dep_id).status != "completed":
            return False  # 依赖没完成 = 被阻塞
    return True

blockedBy 里有任何一个不是 completed，就不能开始。不存在的依赖也视为 blocked——++避免引用错误 ID 时静默通过==。

举个具体的例子，创建一组有依赖的任务：

schema = create_task("setup database schema")
endpoints = create_task("create API endpoints",
                         blockedBy=[schema.id])
tests = create_task("write tests",
                     blockedBy=[endpoints.id])
docs = create_task("write docs",
                    blockedBy=[schema.id])

任务依赖形成一张有向无环图（DAG）：

schema → endpoints → tests
  └────→ docs

schema 是地基，endpoints 和 docs 都依赖它；tests 又依赖 endpoints。Agent 只能按拓扑顺序做——先做没有依赖的，做完解锁下游的。

● ● ●

三个状态，两个动作

两个动作三个状态

pending ──claim──→ in_progress ──complete──→ completed

claim_task：pending → in_progress。设置 owner，开始干活。

def claim_task(task_id, owner="agent"):
    task = load_task(task_id)
    if task.status != "pending":
        return f"Task {task_id} is {task.status}, cannot claim"
    if not can_start(task_id):
        deps = [d for d in task.blockedBy
                if load_task(d).status != "completed"]
        return f"Blocked by: {deps}"
    task.owner = owner
    task.status = "in_progress"
    save_task(task)

claim 会做两个检查：状态必须是 pending（别人没在做），依赖必须全部完成（can_start 返回 True）。两个都过了才能认领。

为什么需要 owner 字段？ 多 Agent 场景下，++防止两个 Agent 同时认领同一个任务==。owner 记录谁在做，其他 Agent 看到 owner 不为空就知道这活有人干了。

complete_task：in_progress → completed。完成的同时解锁下游：

def complete_task(task_id):
    task = load_task(task_id)
    task.status = "completed"
    save_task(task)
    # 扫描所有 pending 任务，找出刚被解锁的
    unblocked = [t.subject for t in list_tasks()
                 if t.status == "pending" and t.blockedBy
                 and can_start(t.id)]
    msg = f"Completed {task_id} ({task.subject})"
    if unblocked:
        msg += f"\nUnblocked: {', '.join(unblocked)}"
    return msg

完成一个任务不只是改状态，还要++扫描所有其他任务，找出"刚刚被解锁"的下游任务==。完成 schema 后，endpoints 和 docs 的 can_start 都返回 True 了——它们可以开始了。

这种"完成即解锁"的设计特别巧妙——++Agent 不需要手动维护依赖关系，完成任务时自动通知==。

● ● ●

持久化：.tasks/ 目录

每个 create_task 写一个 JSON 文件，每个 claim_task / complete_task 更新文件。对话结束了，.tasks/ 目录还在。

跨会话恢复时，Agent 只需要 list_tasks 看一遍：

  ○ task_1700000001_a3f2: setup database schema [completed]
  ● task_1700000002_b7e1: create API endpoints [in_progress] [agent]
  ○ task_1700000003_c1d4: write tests [pending] (blockedBy: task_1700000002_b7e1)
  ○ task_1700000004_e5f8: write docs [pending] (blockedBy: task_1700000001_a3f2)

一眼就能看出：schema 做完了，API 正在做，测试和文档还没开始。++下次开新会话，Agent 读文件就能接着干==。

这和 s09 记忆系统的思路一样——把状态写到磁盘，而不是留在对话里。对话是不可靠的（会被压缩、会丢失），文件是可靠的。

● ● ●

一个容易忽略的细节：不存在的依赖 = 被阻塞

读 can_start 代码时注意到一个防御性设计：

for dep_id in task.blockedBy:
    if not _task_path(dep_id).exists():
        return False  # 依赖文件不存在 = blocked

++如果 blockedBy 里引用了一个不存在的 task ID，视为被阻塞而不是报错==。

为什么？因为如果依赖 ID 写错了（比如拼错了），静默通过比崩溃更危险——Agent 会跳过依赖直接开始，可能基于错误的假设干活。++blocked 是安全默认值==。

这和 s03 权限系统的设计哲学一样——不确定能不能做时，默认拒绝。

● ● ●

对比真实 Claude Code

教学版6字段对比CC9字段

教学版的 Task System 已经很完整了，但读到"深入 CC 源码"那节，发现 CC 走得更远：

CC 的 Task 有 9 个字段，教学版只有 6 个。 CC 多了 activeForm（进行时态，in_progress 时在 spinner 显示）、blocks（下游列表，和 blockedBy 对称）、metadata（任意扩展键值对）。

教学版的 blockedBy 只有上游列表，CC 还维护了 blocks 下游列表——双向引用，方便快速查询。

并发认领的锁机制。 CC 的 claimTask() 用双重锁防竞争：任务文件锁（proper-lockfile 锁住 {taskId}.json）+ 列表级锁（检查 agent 是否已有其他 open task）。锁内重新读取任务（防 TOCTOU），检查三个条件后才设 owner。

教学版的 claim 没有锁——++单 Agent 场景够用，多 Agent 就需要 CC 的锁保护==。

不是 TodoWrite 的升级，是两个独立系统。 CC 中 Task System 和 TodoWrite 同时存在，通过 isTodoV2Enabled() 切换——交互式会话默认启用 Task（V2），非交互式/SDK 默认用 TodoWrite。

为什么要同时保留？ 因为 Task System 有开销（文件 I/O、锁、fs.watch），++简单任务用 TodoWrite 更轻量==。

高水位标防 ID 重用。 .highwatermark 文件记录曾分配过的最高任务 ID。++即使任务被删除，ID 也不会被重用==——避免新旧任务 ID 冲突。

读完对比我最大的感慨是——==教学版把"任务 = 持久化 + 依赖 + 状态机"这个核心讲透了==，CC 在这之上加了并发安全、双向引用、生命周期 hooks。骨架先把 DAG + 持久化讲透，工业级实现后面再展开。

● ● ●

小结

总结 s12 —— TodoWrite 是给 Agent 用的便利贴，Task System 是给 Agent 用的项目管理工具。

从 s05 的内存列表到 s12 的文件持久化任务图，中间跨了 7 节课——但核心变化就三个：有依赖、有状态、持久化。

几个关键设计回顾：

  1. 01blockedBy 形成有向无环图——Agent 只能按拓扑顺序做任务
  3. 02claim / complete 两个动作——pending → in_progress → completed，没有回退
  5. 03完成即解锁——complete_task 自动扫描并报告被解锁的下游任务
  7. 04每个任务一个 JSON 文件——文件系统天然并发安全
  9. 05==不存在的依赖 = 被阻塞==——安全默认值，和权限系统哲学一致

Task System 的本质是"给 Agent 加一层项目管理能力"——不只是列清单，而是管理有依赖、有状态、可恢复的任务图。
