错误不是终点：Claude Code怎么让Agent自己站起来

大家好，我是郑同学。继续肝[旺柴]

上一节 s10 读到结尾，作者留了个钩子：prompt 能运行时组装了，但 Agent 碰到错误还是会崩。网络抖动、API 限流、输出被截断、上下文超限——这些不是 bug，是常态。

我当时就想：前面 10 节攒了循环、工具、权限、Hook、规划、子 Agent、技能加载、压缩、记忆、prompt 组装……这么多机制，结果一个 529 过载就全躺平了？

s11 给出的答案特别直接——错误不是终点，是重试的起点。升级 token、压缩上下文、指数退避、切换模型。

● ● ●

先看一眼"一碰就熄火"是什么样

三种错误三条恢复路径

s10 的循环里，LLM 调用是裸的：

response = client.messages.create(
    model=MODEL, system=system, messages=messages,
    tools=TOOLS, max_tokens=8000)

没有 try/except。API 一报错，整个 Agent 直接崩。三种最常见的故障模式：

输出被截断——模型话说一半，max_tokens 用完了。你让它写个长函数，写到一半戛然而止，代码不完整。

上下文超限——s08 的四层压缩全跑过了，还是太长。LLM 直接拒绝：prompt_too_long。

临时故障——429 限流、529 过载。这不是 bug，是分布式系统的常态。服务端压力大，你被限速了。

一个不处理错误的 Agent 就像一个一碰就熄火的车。跑不了几步就得重启。

● ● ●

解决方案：三种恢复路径

作者的思路是——把 LLM 调用包在 try/except 里，根据错误类型走不同恢复路径。恢复后 continue 回到循环开头重新调用。

三种恢复模式，各管各的错误类型：

模式触发恢复动作
输出截断max_tokens升级 8K→64K / 续写提示
上下文超限prompt_too_longreactive compact → 重试
临时故障429 / 529指数退避 + 抖动，连续 529 切备用模型

关键设计：三种恢复机制各管各的错误类型，互不干扰。截断走截断的路径，超限走超限的路径，限流走限流的路径。错误分类是恢复的前提。

● ● ●

路径一：输出被截断，升级 token

截断先别追加输出

模型话说一半，max_tokens（默认 8000）用完了。

第一次发生时，不追加截断输出，直接把 max_tokens 从 8K 升到 64K（8 倍空间），重试同一个请求：

if response.stop_reason == "max_tokens":
    # 第一次升级：不追加截断输出，保持原始请求不变
    if not state.has_escalated:
        max_tokens = ESCALATED_MAX_TOKENS  # 64000
        state.has_escalated = True
        continue  # messages 不变，同一请求给更多 token

为什么不先追加截断输出？ 因为截断的那段输出是不完整的——可能截在函数定义中间、截在代码块里。如果追加到 messages 再重新发，模型会基于不完整的内容继续，容易产生重复或混乱。直接重发原始请求，只是给更多空间，让模型从头完整输出。

64K 还是不够怎么办？ 这时候才保存截断输出，注入续写提示让模型接着说：

    # 64K 还是被截断：保存输出 + 续写提示
    messages.append({"role": "assistant", "content": response.content})
    messages.append({"role": "user", "content":
        "Output token limit hit. Resume directly — "
        "no apology, no recap. Pick up mid-thought."})
    state.recovery_count += 1
    continue

续写提示很讲究——"no apology, no recap"（别道歉、别复述）。因为模型被截断后，续写时最喜欢说"抱歉，我刚才说到……"然后重复一遍前面的内容。这句提示就是堵住这个毛病。

升级只有一次机会，续写最多 3 次。超过就退出——++继续续写也不会有实质产出==。

● ● ●

路径二：上下文超限，reactive compact

LLM 说"你的上下文太长了"。s08 的四层压缩（snip→micro→budget→auto_compact）全跑过了，还是超。

触发 reactive compact——比 auto compact 更激进的紧急压缩：

except PromptTooLongError:
    if not state.has_attempted_reactive_compact:
        messages[:] = reactive_compact(messages)
        state.has_attempted_reactive_compact = True
        continue
    return  # 压缩过了还是超限，只能退出

教学版的 reactive_compact 做了简化——只保留最后 5 条消息，前面全砍。真实实现会调 LLM 生成 compact 摘要再重试。

为什么只压一次？ 因为压缩后再超限，说明消息本身就是超大单条（比如一个巨大的 tool_result）。++再压缩也不会变小，只会浪费一轮 API 调用。不如直接退出，让用户知道上下文确实撑不住了==。

读到这儿我想到 s08 的教训——压缩是最后的手段，不是万能药。s11 的 reactive compact 是 s08 压缩管线的"紧急出口"，用完就没了。

● ● ●

路径三：临时故障，指数退避

退避要加随机抖动

网络抖动、429 限流、529 过载——这些不是 bug，是分布式系统的常态。

429 和 529 统一走指数退避 + 抖动：

def retry_delay(attempt, retry_after=None):
    if retry_after:
        return retry_after
    base = min(500 * (2 ** attempt), 32000) / 1000
    return base + random.uniform(0, base * 0.25)

退避公式：min(500 × 2^attempt, 32000) + random(0~25%)。

尝试基础延迟+ 抖动
10.5s0-0.125s
21s0-0.25s
44s0-1s
7+32s（上限）0-8s

为什么要加随机抖动？ 因为如果多个客户端同时被限流，它们会在同一时刻重试，造成"惊群效应"——服务器刚喘口气又被轰。抖动让每个客户端错开重试时间。

如果服务器返回了 Retry-After header，优先用那个值——服务端最清楚自己多久能恢复。

连续 3 次 529 过载 → 切换到备用模型：

if state.consecutive_529 >= 3 and FALLBACK_MODEL:
    state.current_model = FALLBACK_MODEL

为什么是 3 次而不是 1 次？ 因为偶尔一次 529 可能只是瞬时高峰，重试就好了。连续 3 次说明服务端确实过载严重，这时切换模型比继续等更靠谱。

● ● ●

合起来：循环里的恢复时机

def agent_loop(messages, context):
    state = RecoveryState()
    max_tokens = 8000
    while True:
        try:
            response = with_retry(  # ← 处理 429/529
                lambda: client.messages.create(
                    model=state.current_model,
                    max_tokens=max_tokens, ...),
                state)
        except Exception as e:
            if is_prompt_too_long_error(e):  # ← 路径 2
                messages[:] = reactive_compact(messages)
                continue
            return  # 其他错误：退出

        if response.stop_reason == "max_tokens":  # ← 路径 1
            # escalate or continuation...
            continue
        # 正常流程
        messages.append(...)

三层防线，各管各的：

  •  with_retry 处理瞬态错误（429/529）——指数退避在循环最内层
  •  外层 except 处理上下文超限——reactive compact 后重试
  •  stop_reason 检查 处理输出截断——升级 token 或续写

++错误恢复的关键不是"try 住所有异常"，而是"分类处理不同类型的错误"==。

● ● ●

RecoveryState：跨轮次的恢复记忆

恢复不是无状态的——升级过了没？压缩过了没？连续几次 529？ 这些要跨轮次记住：

class RecoveryState:
    def __init__(self):
        self.has_escalated = False          # token 升级过了没
        self.recovery_count = 0             # 续写了几次
        self.consecutive_529 = 0            # 连续几次 529
        self.has_attempted_reactive_compact = False  # 压缩过了没
        self.current_model = PRIMARY_MODEL  # 当前用的模型

为什么要记这些？ 因为恢复动作有上限：

  •  升级只有一次（8K→64K，不会再升到 512K）
  •  续写最多 3 次（再多也没实质产出）
  •  reactive compact 只有一次（再压也不会变小）
  •  529 连续 3 次才切模型（避免频繁切换）

没有 RecoveryState，Agent 会无限重试同一个错误。有了它，每种恢复都有明确上限，到了上限就体面退出，不死循环。

● ● ●

一个容易被忽略的细节：截断检查在 append 之前

读代码时我注意到一个关键的顺序——max_tokens 检查在 messages.append 之前：

# ✗ 错误顺序：先 append 再检查
messages.append({"role": "assistant", "content": response.content})
if response.stop_reason == "max_tokens":
    ...  # 截断输出已经进 messages 了

# ✓ 正确顺序：先检查再决定要不要 append
if response.stop_reason == "max_tokens":
    if not state.has_escalated:
        continue  # messages 不变，直接重试
    messages.append(...)  # 只有续写时才 append
messages.append({"role": "assistant", "content": response.content})  # 正常才 append

为什么顺序重要？ 第一次升级时不追加截断输出——让模型用更大空间从头完整输出。如果把截断输出先 append 了，模型就会基于不完整内容继续，产生重复或错乱。

这种"先检查再执行"的顺序，和 s03 权限系统一样——先判断能不能做，再做。不是做完再后悔。

对比真实 Claude Code

教学版3条对比CC十几种

教学版的三种恢复路径已经很清晰了，但读到"深入 CC 源码"那节，我才发现真实 CC 走得更远：

CC 有十几种 reason/transition，不止 3 条。 教学版只展开了最常见的 5 种。CC 还有 collapse_drain_retry（context collapse 先提交暂存）、aborted_streaming（流式中止恢复）、stop_hook_blocking（hook 注入 blocking error 让模型自纠）、token_budget_continuation（token 用量 < 90% 时继续）等。

教学版是骨架，CC 是完整免疫系统。

流式错误处理：可恢复的错误被"暂扣"。 CC 的流式路径中，可恢复的错误（413、max_tokens、media error）在 streaming 期间不展示给用户——SDK 消费者看不到，只有恢复逻辑能看到。等 streaming 结束后才判断是否需要恢复。

这个设计很聪明——用户不需要看到"出错了"再看到"恢复了"，全程无感知。

Diminishing Returns 检测。 Token budget 的"继续"不是无限的。当连续 3 次 continuation 且 token 增量 < 500 时，系统判断"继续也没有实质性产出"，停止 continuation。

++防止模型空转烧 token==——续写了 3 次但每次只多写几个字，就该停了。

529 → Fallback Model 切换的用户提示。 CC 切换模型时会清除所有 pending 消息和 tool 结果，给用户展示 "Switched to {model} due to high demand"。教学版只是默默换了 current_model，用户完全不知道。

读完对比我最大的感慨是——==教学版的三条路径是"能恢复"，CC 的十几种是"优雅地恢复"++。骨架先把"分类处理 + 重试上限"这个核心讲透，工业级实现后面再展开。

小结

读完 s11，我自己最大的感悟是——错误恢复让 Agent 有了"韧性"。

前 10 节的 Agent 跑得顺的时候很强，但一碰就碎。s11 之后，++Agent 能在错误中自己爬起来==——截断了续写，超限了压缩，限流了退避，过载了换模型。

四个关键设计回顾：

  1. 01三种恢复路径各管各的错误类型：截断→升级token、超限→reactive compact、临时故障→指数退避
  3. 02每种恢复都有明确上限：升级 1 次、续写 3 次、压缩 1 次——到了上限体面退出
  5. 03指数退避必须加抖动：防止惊群效应，Retry-After 优先
  7. 04RecoveryState 跨轮次记忆：升级过没、压缩过没、连续几次 529

几个关键点：

  1. 01s11 加了 with_retry / retry_delay / reactive_compact / RecoveryState / is_prompt_too_long_error
  3. 02截断检查在 messages.append 之前——先判断能不能做，再做
  5. 03续写提示 "no apology, no recap"——堵住模型复述前文的毛病
  7. 04529 连续 3 次才切模型——偶尔一次是瞬时高峰，连续 3 次是真过载
  9. 05CC 有十几种 reason，流式错误暂扣不展示，Diminishing Returns 检测防空转

错误恢复的本质是"给 Agent 加一层免疫系统"——不是不生病，而是生病了能自己扛过去。
