## 3. 关键设计决策

### 3.1 Plan Mode 的"白名单 + 保守拦截"二选一
选了**保守拦截**（只拦声明了 `write/exec/delegate` 的工具）而非严格白名单。原因：
- 未来新加的工具如果忘记声明 `requires`，白名单会误拦
- `requires` 标签是 TOOLS.md §0.4 的显式约定，拿它做 gate 比另起一个清单更自洽
- `_PLAN_ALLOWED` 里只显式列 ExitPlanMode、AskUserQuestion 等几个**必须可用**的工具，覆盖极端情况

### 3.2 BackgroundKill 为什么用进程组（setsid + killpg）
- Bash 通过 `shell=True` 启动，父进程是 `/bin/sh`，实际任务往往是子孙进程（`sh -c "node server.js"`）
- 单 `proc.kill()` 只能杀 shell，node 进程继续跑
- `os.setsid` 让子进程新建一个进程组；`os.killpg(pgid, SIGTERM)` 整组杀
- Windows 没这套语义 → fallback 到 `proc.kill()`

### 3.3 AskUserQuestion 用 ask_holder 做依赖反转
问题：`register_ask_user` 时 Repl 还没构造（Repl 需要 registry），但 Repl 构造后才能注册真实交互实现。

解法：CLI 传一个 `dict["fn"]` 到两侧，Repl 构造时**原地改写** `ask_holder["fn"] = self._interactive_ask`。工具 handler 每次调用都重新取最新函数。这样避免循环依赖。

### 3.4 MultiEdit 为什么不用文件锁
- 原子性这里是"对该文件的一次 write_text 调用完成前不会产生部分写入"—— Python 的 `path.write_text` 在 macOS/Linux 底层是单次 `write()` 系统调用
- 如果真遇到并行 MultiEdit 到同一文件：dispatcher 在同路径串行化规则里已经拦掉了
- 跨进程并发场景（mycode 和别的进程同时改）不是我们的威胁模型

### 3.5 WebFetch 为什么不用 BeautifulSoup
- 多加一个 140 KB 的依赖，只为了我们用三行正则能搞定的事
- 正则版对畸形 HTML 容忍度**更高**（BS 偶尔会在极怪 HTML 上崩）
- 代价：复杂文档的信息提取质量不如 BS，但"读 README / API 文档"这种结构化页够用

### 3.6 WebFetch 的 URL 白名单留给后续
- 目前只拦 `file://` / `ftp://` 等非 http 协议
- 未来如果想加"不能访问内网"规则，要引入 DNS 解析 + CIDR 匹配，工作量更大
- M5 若补权限模型再统一做

## 4. 已知限制

1. **队友 auto-compact 未做真实 LLM 集成测试**：我们只测了"signature 层面 summarize_llm 参数正确传到 start_teammate_loop"，没跑起真的队友线程 + 触发压缩。极长会话队友场景未验证过
2. **BackgroundKill 的 Windows 支持**：只 fallback 到 `SIGTERM`，没测过；Windows 上是否真能终止子孙进程未知
3. **AskUserQuestion 在 REPL 里阻塞**：用户需要手动输入数字。如果用户已经按 Ctrl-C 取消整轮，而工具此时正在等数字，状态机可能停在奇怪位置。测试里只覆盖了 KeyboardInterrupt fallback 路径
4. **Plan Mode 和多 Agent 不完全正交**：如果主 agent 进了 plan mode 然后派了一个 teammate，teammate 的 write 工具不会被 plan gate 拦截（因为 teammate 有自己独立 state）。不是 bug，是预期行为，但可能反直觉
5. **WebFetch 的 HTML→text 对 JS 渲染页无效**：只能看服务端返回的静态 HTML；SPA 页面几乎是空的
6. **MultiEdit 不触发 "must Read first" 检查**：Write 有这个保护（session 内必须先 Read），MultiEdit 没做。原因是 MultiEdit 只改现有文件（必然已存在），比 Write 少一层误覆盖风险，但严格说也应该加
